# backend-cpp

The game server. CMake + vcpkg, built and run from CLion or the terminal.

```bash
cmake --preset debug
cmake --build build
./build/backend_cpp        # ws://localhost:9001
```

## First time on a machine

```bash
../../tools/install-cpp-deps.sh
```

Installs the host toolchain (cmake, ninja, and the autotools libsodium's build
needs) and bootstraps vcpkg into `~/vcpkg`. Everything else comes from
[`vcpkg.json`](vcpkg.json), pinned by `builtin-baseline`.

CLion works either way: with the `debug` preset, or with a profile of its own
into `cmake-build-debug/`. `CMakeLists.txt` locates vcpkg itself (`VCPKG_ROOT`,
else `~/vcpkg`) and pins `VCPKG_INSTALLED_DIR` to `build/vcpkg_installed`, so
every profile shares one dependency tree instead of building its own.

## Architecture

One thread, one event loop. uSockets polls the sockets; a `us_timer_t` on the
same loop drives `World::Tick` at 20 Hz. They are peers — neither drives the
other.

Socket callbacks never mutate the world. They enqueue commands, and the tick
applies them, so ordering belongs to the simulation rather than to the order
packets happened to arrive.

`game/world.h` must never reference uWebSockets, uSockets or libuv. CMake enforces
this: the `slime_world` target does not link `uwebsockets`. That seam is what
keeps `Tick()` testable headless, and what would make moving the simulation to
its own thread a move rather than a rewrite.

### On libuv

Earlier notes in this repo described owning a `uv_loop_t` and attaching uWS to
it. That does not apply here: **vcpkg builds uSockets against epoll on Linux**
— its `CMakeLists.txt` guards the libuv backend with `if(WIN32 OR ANDROID)`.
There is no uv loop to own, `libuv` is not a dependency of this project, and
the tick is a `us_timer_t` rather than a `uv_timer_t`.

Driving the loop yourself (`uv_run`) with this port silently half-works: the
process listens and the timer fires, but no socket is ever polled.

## Generated code

C++ FlatBuffers code is generated **at build time** into
`build/generated/common_generated.h` by a CMake custom command. `flatc` comes
from the same vcpkg port as the C++ headers, so the version match that
generated code `static_assert`s on holds by construction — nothing to keep in
sync by hand, and nothing generated is committed.

The **TypeScript** client is still generated by
[`../schema/generate.sh`](../schema), which writes into `src/frontend`. Run it
after editing a `.fbs`; the C++ side needs no action beyond rebuilding.

**The two sides use different flatc versions, deliberately.** Generated code
must match its own runtime, and those runtimes move independently: vcpkg's C++
port is at 25.12.19 while npm's `flatbuffers` caps at 25.9.23. So C++ uses
vcpkg's flatc and TypeScript uses the pinned one in `~/.local/bin`. The two
happen to emit identical TS today, but that is not a guarantee to lean on —
don't "simplify" `generate.sh` to reuse the vcpkg binary.

## Dependencies

| Package | Why |
|---|---|
| `uwebsockets` (+`zlib` feature) | WebSocket server and pub/sub. The `zlib` feature is **not** default — without it `SHARED_COMPRESSOR` silently does nothing. |
| `entt` | ECS. `World` owns the registry. |
| `flatbuffers` | Wire format, and `flatc` for codegen. |
| `libsodium` | Credential storage for the register/login endpoints. Wired into the build, not yet called. |
